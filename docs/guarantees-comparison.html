速くするために、どの保証を外せるか

安全性を保つ処理と、内部表現のコストは別です。凍結を外すだけでは、公開定義・検証・CLI metadata の整合性が崩れる可能性があります。

まず内部表現を見直し、スキーマの変更を許すかどうかは別途決めるのが望ましいと考えます。

この資料は比較と変更案です。ライブラリの仕様は変更していません。

判断の要点現在の勝ち負け変更とデメリット3 ライブラリの実行例進め方の提案確認範囲と出典

「保証が違うから負ける」とは、まだ言い切れません

過去の切り分けでは、shape のコピー・凍結や入力の own property チェックにコストがありました。一方、それらを保ったまま固定キーの検証を生成することで、大きな object の性能差を改善できています。仕様の差と、実装上の最適化余地が両方あります。

  • Standard Schema が要求するもの：~standard に version / vendor / validate を持ち、成功時の value と失敗時の issues / path を所定の形式で返すこと。shape のコピー・凍結、独自 metadata、クラス、早期 Map 作成は要求されません。Standard Schema 仕様
  • Loculus の用途で保ちたいもの：入力や prototype を安全に扱い、RHF が正しいフィールドにエラーを表示し、Politty の help と実際の検証を一致させること。
  • 見直しやすいもの：metadata の表現、~standard の実体化タイミング、検証コードの共有。スキーマの同一性や挙動を変えずに行える可能性があります。

Zod の「Immutable API」はメソッドが新しいスキーマを返すという意味で、shape の実行時凍結を意味しません。Zod の .readonly() は解析後の出力を凍結する機能。Valibot の readonly() は出力の型を readonly にし、今回の実装では実行時凍結をしません。shape の凍結とは別の話です。Zod · Zod readonly · Valibot readonly

現在、負けているのはどこか

既存の 107 プロファイルの比較では、対 Zod の実用上・統計上の負けは 0、対 Valibot は次の 5 条件です。全て「スキーマ作成＋有効入力の 1 回検証」。反復の有効・無効入力では、この判定基準での対ライブラリの負けは残っていません。

保証のコストを切り分けた過去の実験

whole-object 最適化前の strict object「作成＋1 回」で、凍結だけを外すと Node 125→102 ns、Bun 88→77 ns。Valibot にコピー・凍結・own property チェック・配列拒否を追加すると Node 91→122 ns、Bun 68→87 ns でした。これは当時の fixture の結果で、現在の空 object や literal の値から差し引ける数値ではありません。

同じ時期の 100 フィールドの反復検証では、own property チェックを保持した固定キー生成が Node 2,902 ns / Bun 846 ns、Valibot は 12,220 ns / 1,023 ns。保証を外さずに勝てた実験が、その後の whole-object 最適化の根拠です。

凍結は作成時の処理なので、作成を計測しない反復の遅さを直接説明しません。残る 5 条件について、各保証の寄与を全て分離した証拠はありません。

何を変えると、どんなデメリットがあるか

設計と型の修正が必要

1. shape の凍結だけをやめる

比較：Loculus は作成時のコピーを凍結。Zod は最初に shape を読むとコピーしますが凍結しません。Valibot は渡した entries をそのまま保持します。

具体的な不利益：schema.shape.name を number に置き換えたつもりでも、Loculus の親は作成時の string 検証関数を保持しています。凍結だけ外すと TypeError が消え、「定義は number、検証は string」という静かな不整合になります。Politty が shape を読むと、help や選択肢にも食い違いが出る可能性があります。

現在の型は readonly shape: S で、shape プロパティ自体の代入は禁止しても、中の name の代入までは常に禁止しません。Readonly<S> 等の型整理も必要です。TypeScript の readonly だけでは JavaScript や Reflect.set による変更を防げません。

判断：「作成後の変更は未サポート」という契約を明示し、公開定義と検証の整合性を設計してから検討。開発時だけ凍結する案は事故検出を保てますが、本番だけ変更が通る差が増えます。現状から凍結 1 行だけを削除するのは避けたいです。実行例 3

凍結解除より影響が大きい

2. 元の shape のコピーをやめる

具体例：共通の CLI 定義から schemaA を作り、同じ shape を編集して schemaB を作る。参照を共有すると schemaA まで変わる可能性があります。フォームでも、管理者用に追加した項目が一般ユーザー向けに流れ込む原因になります。

同じ参照を凍結する方法では、逆に呼び出し側の shape まで凍結してしまいます。コピーを省くだけでは、どちらの問題も解決しません。

判断：通常 API は作成時 snapshot を維持する方が扱いやすいです。生成 plugin が自分で作る外部に共有されない shape は、現状でもコピーせず凍結しており、利用者の定義を巻き込まずに省略できています。実行例 1 · 実行例 2

まず検討したい内部最適化

3. metadata のクラス・setter・作成タイミングを見直す

Loculus の EnumMeta クラスや enumValues setter は Standard Schema の要件ではありません。Politty は kind / optional / defaultValue / description / enumValues / shape を読むため、それらの値と意味を保てば、クラスの表現は変えられます。Zod は registry の metadata、Valibot は pipeline の metadata action を用い、Loculus と同じ構造ではありません。Zod metadata · Valibot metadata

現在でも起こる問題：literal("ready") の metadata を Reflect.set で enumValues=["other"] にすると、表示用選択肢は other、検証は ready のままです。setter を残すことが整合性の保証にはなっていません。通常の TS API では enumValues は readonly ですが、実行時の setter は動きます。

const field = l.literal("ready");
Reflect.set(field.meta, "enumValues", ["other"]);
field.meta.enumValues;          // ["other"]
l.safeParse(field, "ready");   // success
l.safeParse(field, "other");   // failure

変更のデメリット：setter 廃止では、この実行時書き換えができなくなります。遅延 metadata では getter の処理や初回読取のコストが増えます。検証済み値に無関係な label を表示したい場合は、検証用 enumValues と分けた UI 定義を使う必要があります。

判断：意味が変わらない読み取り用 metadata を作り、書き換えを許さない設計を検討。今の enumValues は既に遅延生成なので、クラスを平坦な配列に置き換えて常に配列を作ると、むしろ作成が遅くなる可能性があります。クラス廃止そのものの速度向上は未計測です。

何を共有するかでリスクが違う

4. metadata・検証コード・スキーマ本体を共有する

検証コードだけ：設定・default 値の参照・closure の意味を保てば、同じ処理を共有する余地があります。metadata：書き換え可能なまま共有すると、コマンド A の description を変えただけで B の help も変わります。今の metadata 全体は凍結されていません。

スキーマ本体：同じ l.string() を常に同じオブジェクトにする案は避けたいです。Politty の引数 metadata や抽出キャッシュはスキーマの参照をキーにするため、同じ型の userName と password の設定が混ざる原因になります。Zod の metadata registry もスキーマの同一性を使います。

判断：外側のスキーマは毎回別のまま保ち、読み取り専用の内部データや検証コードの共有を先に試す。参照同一性・default の可変参照・メモリ量を確認します。無制限の literal キャッシュは保持メモリと初回コストが増え、別のトレードオフになります。実行例 6

仕様を保てる候補

5. ~standard をアクセス時に作る

Zod は既に遅延実体化、今回の Valibot と Loculus は eager に作成します。Standard Schema は own property として最初から存在することも、別スキーマ間での参照の独立性も要求していません。

不利益：Object.hasOwn(schema,"~standard") の結果が変わります。Object.keys や spread 等、反射による列挙・コピーの挙動も設計と確認が必要です。初回アクセス時の負荷は増え、Loculus の safeParse はすぐ ~standard を読むため、「作成＋1 回」では遅延するだけでコストが消えるとは限りません。

判断：公開アクセス schema["~standard"].validate が同じ結果を返すこと、Politty / RHF で使えること、同じ schema の再アクセスは安定することを保って検証できます。作成数・使用率ごとの計測が必要です。

入力境界では維持したい

6. own property チェック・配列拒否・__proto__ 処理を省く

own property：必須の name を送信していない入力でも、prototype の name が採用されるようになります。許すなら「継承された設定を受ける機能」ですが、CLI / フォーム用途で意図せず必須チェックを通る不利益の方が大きいと考えます。

配列拒否：空 object が [] を成功扱いし、JSON 設定の取り違えを見逃します。__proto__：通常の代入に置き換えると、object 値を代入した場合に出力の prototype が変わり得ます。安全な own property の書き込みを保つか、キーを明示的に拒否する必要があります。

__proto__ を正規の項目名として許す機能は必須とは限りません。拒否すればその名前のフォーム項目や設定が使えなくなります。安全性は保ち、名前のサポート可否だけを別に決めるべきです。実行例 4 · 実行例 5 · 実行例 8

RHF の結果や操作回数に影響

7. エラーの clone・全件収集をやめる

clone を省く例：同じ custom field が共有・凍結された issue を返し、left と right の両方で使われる場合。path をその場で変更すると TypeError になったり、以前の left が right のエラーにも混入したりします。Loculus はコピーして prefix を付け、元の issue を変更しません。

const sharedIssue = Object.freeze({
  message: "shared", path: Object.freeze(["leaf"])
});
// Observed when the same custom field is used for left and right
// paths: ["left", "leaf"], ["right", "leaf"]
// sharedIssue.path remains ["leaf"]

Valibot の object 内部は子 issue の path を直接 prepend します。ただし各ライブラリの拡張 API・issue の構造は違い、この Loculus custom field をそのまま他ライブラリに渡す比較ではありません。

全件収集を省く例：未知の extra1 / extra2 を最初の 1 件だけ返すと、フォーム修正や設定の修正を複数回繰り返すことになります。Zod の 1 件は集約で両キーを示すため、「件数が少ない＝情報が少ない」ではありません。

判断：RHF 用の path と generic な子の issue 保護は維持。生成コードが自分で作る新しい issue だけを直接構築する最適化なら、共有 issue の保護を外す必要はありません。未知キーの全件収集を選択式にする案はありますが、成功入力での作成コストの負けは説明できません。実行例 9

拡張と副作用の挙動が変わる

8. 子の関数 capture・入力の読取順を変える

子関数を毎回取得する設計では、作成後の子の差し替えが親にも反映されます。Loculus は今は capture します。変更を禁止するなら capture は実装上の選択ですが、変更を許すなら validation / metadata / キャッシュの更新を一貫して扱う必要があります。

入力をまとめて先読みする最適化では、getter や callback が後続フィールドを変えるケースで結果が変わります。実測した getter a が b を "before"→"after" にする例では、Loculus は {a:"first", b:"after"} を返しました。先読みで b を確定させると before が残ります。

判断：通常の CLI / JSON のプレーンなデータでは問題になりにくいものの、一般の object を受ける API の挙動変更です。直接固定キーを生成しても、読取→検証→書込をフィールド順に保てば、この保証を落とさずに最適化できます。実行例 7

エラー検出時点のトレードオフ

9. discriminated union の早期検査を遅らせる

kind:"deploy" が 2 分岐に重複した場合、Loculus は定義時に止まります。Zod は最初の検証で例外。今回の Valibot は受理しました。分岐の不備を起動時に知るか、その操作を実行した時に知るかが変わります。

不利益：遅延すれば使われない不正なスキーマは気付かれないまま残ります。Politty は help や variant 抽出でも metadata を読むため、検証だけ遅延しても CLI 初期化で必要な処理が残る可能性があります。

判断：早期検査を保つかは外向けの設計判断ですが、Map 構築を後ろに移すだけでは現在の単発計測の total は減りません。静的生成で重複を検出するなど、実行時の仕事を実際に減らす方法と区別します。実行例 10

進め方の提案

  1. 既存の安全な入力処理と RHF の path を保持する。これらの保証を外さずに改善できた実績があります。
  2. まず内部表現を試す。enum metadata の読み取り専用化、遅延 ~standard、内部検証コード共有を別々に測定。setter・クラス・割当回数は外向けの仕様と分けて扱います。
  3. shape の変更契約を決める。通常 API は作成時 snapshot を保ち、型も中の項目を readonly にする案を推します。凍結の dev 限定化や廃止は、変更をした時の失敗の仕方も含めて評価します。
  4. 残る 5 条件を個別に切り分ける。literal は metadata / 関数・結果の割当、空 object は snapshot / 凍結 / 入口チェック、union は early check / index 構築を独立に変え、作成＋1 回の総時間・反復・gzip・型・Politty / RHF の結果を確認します。
「保証を外せば Valibot に必ず勝つ」「クラスを消せば速くなる」という証拠は、まだありません。ここでは変更候補と具体的な代償までを示し、未計測の速度向上は約束していません。

利用者側での推奨は、既存 schema を書き換えるより、目的ごとに新しい schema を作ること。動的フォームでも定義の更新と resolver の更新を合わせれば、推論型・検証・表示の食い違いを避けやすくなります。
